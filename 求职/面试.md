# 项目面试手册

> 仅依据当前 2.4 版项目及其对应结果。项目介绍与重点案例采用 STAR：背景（Situation）—任务（Task）—行动（Action）—结果（Result）。这里给出可复查的设计依据、权衡与回答提纲，第一人称示范需与本人实际职责对应。

## 一、先建立准确的项目定位

**一句话：围绕两类已有 Skill，开发可复跑的评估工具，验证 Agent 是否真正按用户要求完成任务，并用证据定位失败层级。**

两类业务任务是：①把本地性能数据转成数据库报告；②使用结构化数据和资讯核查金融回答。两套业务 Skill 是被测对象，新增工程重点在 `run.py`、`judge.py`、`tool.py`、`review.py`、`collect.py`、校准测试和用例资产。

它解决的核心问题是：Agent 输出了内容、程序退出 0、工具返回了数据，都不足以证明用户任务完成。必须把原始输入、任务范围、工具证据、最终答案和交付要求接起来验证。

### 60—90 秒介绍｜测试开发

> **S｜背景：** 我的项目评估数据库性能报告和金融核查两类 Skill。输出具有非确定性，脚本跑通、报告存在，也可能出现数据失真或用户要求遗漏。
>
> **T｜任务：** 项目目标是建立可复跑的自动化评估工具，准确判断任务是否完成，区分业务缺陷与运行阻塞，并提供可定位的失败证据。
>
> **A｜行动：** 我围绕需求和风险设计了 44 条用例，用 Python 实现组件、流水线和 Agent 执行入口，另设真实依赖检查；通过独立 oracle 核验原始数据、筛选范围、数值口径及引用，并用正反例校准裁判，自由文本单独做哈希绑定的 LLM 复核。
>
> **R｜结果：** 当前 38 项裁判校准全部通过；20 条数据库组件用例检出 9 条失败，6 次流水线均未满足完整验收，定位了 300 秒误读为 2026 秒、零值与空值混淆、专项分析遗漏 P99 等问题，形成证据与回归条件。业务 Skill 的修复后回归尚未完成。

### 60—90 秒介绍｜Agent／AI workflow

> **S｜背景：** 两类已有 Skill 涉及报告生成和金融核查，仅看最终回答，难以确认 Agent 是否实际调用工具、引用有效证据并完成用户意图。
>
> **T｜任务：** 我需要建立可复跑、可追溯的 Agent 执行与评估框架，把任务输入、工具取证和完成度判断连接起来。
>
> **A｜行动：** 我用 Python 和 Codex CLI 构建独立会话执行链路，提供固定输入、时钟和 Skill 快照；用子进程工具替身固定证据、模拟依赖失败，收集事件与回执，再以 JSON Schema、独立 Judge 和 LLM 复核分别检查结构、事实及解释。
>
> **R｜结果：** 项目形成 44 条场景用例，主模型金融受控基线 22/22 通过并完成 LLM 复核，另外保留重复和第二模型的小样本结果。当前成果是工作流编排与工具调用评估，尚未接入多厂商原生 Function Calling，也不代表真实金融端到端成功。

### STAR 讲述时的重点

S 说明用户和问题，T 说明验收目标，避免重复背景；A 重点讲本人采取的动作、为什么这样做以及证据；R 报告已经发生的结果。时间可按 S 约 10 秒、T 约 10 秒、A 约 35—45 秒、R 约 15—20 秒分配。

本项目的结果可以是“检出并定位失败”“形成可复跑基线”，不必编造效率提升。修复建议属于下一步，不能放进 R 冒充修复已生效。

## 二、我是怎样分析这个项目的

### 1. 先确定“最新版本”和事实边界

以 `答卷/manifest.json` 的 2.4 版本为锚，查看 `README.md`、`评估.md`、`结果.md`，再核对正式输出目录。目录中保留的其他运行是过程证据，不把不同协议、不同模型或不同层级的最好成绩拼成一个总通过率。

判断一条成果能否写进简历，要同时找到：**当前实现、对应输入、实际运行记录、最终判定、适用范围。** 只有设计而无执行的内容，写作方案或下一步；只有结果而无个人职责的内容，不推定为本人独立开发。

### 2. 从用户任务建立验收合同

数据库报告不是“生成一个文档”，而是数据不失真、分析范围正确、结论有依据、格式可交付。金融核查不是“调一个查询接口”，而是对象、日期、市场、币种、报告期一致，判断由证据支持。

要求分三种来源：用户明确要求、Skill 与 references 的明确约束、评测补充约定。用户要求比较 P99，不能因为实现没做就改为加分项。金融证据不足时使用 null，则应说明是本项目补充的评测约定，不能声称原 Skill 已完整定义。

### 3. 画出执行链，按层找可观察证据

```text
用例配置（公开 input / 裁判 gold / 覆盖标签）
        ↓
执行器 run.py
  ├─ component：直接调用业务组件
  ├─ pipeline：运行完整业务脚本，保存产物
  └─ agent：独立 CLI 会话，加载 Skill，调用工具，交付答复
        ↓
独立 Judge：检查数值、范围、引用、状态、文件
        ↓
语义复核：审阅解释与限制，绑定响应哈希
        ↓
逐例结果 / 汇总报告 / 缺陷定位与回归建议

live.py：单独调用真实金融依赖，检查真实回执
```

四层分别回答“组件对不对”“脚本能否完整交付”“Agent 是否正确执行与答复”“真实依赖返回什么”。层级互补，不能互相替代。

### 4. 用场景矩阵检验覆盖，而不是只数用例

| 维度 | 实际设计 | 检验的问题 |
| --- | --- | --- |
| 正常路径 | 四种报告、金融 0/1/2、仅问题入口 | 能否完成基本任务 |
| 数据等价性 | 同源 90 条 JSON／CSV／XLSX | 格式变化是否改变数据 |
| 边界值 | 0 与 null；2.99%、3.00%、3.01% | 是否混淆缺失、零值、等号 |
| 逻辑组合 | 中英文 AND／OR、场景与并发组合 | 筛选集合是否忠于用户 |
| 前提条件 | 版本不足、公平性、空数据、坏路径 | 不满足分析前提时是否限制或停止 |
| 故障配对 | 请求相同，仅工具状态改变 | 能否把行为变化归因到依赖故障 |
| 口径 | 日期、币种、市场、报告期、指标周期 | 是否用不相干证据支持结论 |
| 安全与越界 | 内部链接、假密钥、资料指令注入 | 是否正确拒绝、停止并避免泄露 |

44 条是当前测试资产规模，不是穷尽覆盖，也不代表 44 条完整端到端测试全部跑过。

### 5. 为正确性找到独立参照

数据库日志 oracle 锚定原始 `Duration:`、`DB:` 和性能行，不调用被测解析器。金融财报参考 `sources.json` 保存的官方年报字段与来源，明确亿元换算和容差。受控行情与事件是合成夹具，不能当真实市场事实。

独立参照的目的，是防止同一个错误同时进入实际值和预期值。例如三个格式都写 2026 秒，只能说明复制一致，不能说明正确。

### 6. 把“执行状态”“业务判断”“质量分数”拆开

金融的 0/1/2/null 是候选答案真实性分数；Judge 的 0—100 是本批适用检查的质量评分；PASS／FAIL／BLOCKED 等是执行与测试状态。三个维度不能互换。

mandatory 用来守住必须完成的要求；fatal 用来标记严重错误并将该用例归零。保留部分得分便于定位，但高分不能掩盖当前用例必需项失败。N/A 不当成 0，也不当成通过。

### 7. 验证裁判本身会不会错

准备正确输出与故意破坏的输出：改时长、改 QPS、把正确数字放错行、删必需文件、伪造引用、混淆未知与错误、泄露 canary。当前 38 项校准全部通过，说明裁判能处理这些已知情况，不能证明它永远正确。

遇到裁判误杀，修复规则、补正反例，再对同批原始输出统一重判。改变输入或工具证据则必须重跑 Agent。

### 8. 追到原始证据，再解释根因

读汇总报告只能发现现象；定位必须回到 `actual.json`、原始输入、业务源码、工具回执和事件轨迹。把“确认的事实”“代码支持的原因”“尚未验证的猜测”分开。

例如 0/null 问题有代码中的 `or` 兜底支撑；接口财报数据与官方口径冲突，则尚不能直接指控模型编造，应继续检查字段、汇率转换和报告币种。

### 9. 按风险与证据安排下一步

先修数据失真和错误事实放行，再修用户范围与门控，再补交付和语义，最后看性能成本。修业务 Skill 时使用新副本，在冻结用例和 Judge 下对照回归；当前没有这批修复后结果。

## 三、对截图“Skills 和工具调用”的逐项回答

### Q1：Skill 是什么，和 Prompt、Tool、MCP 分别是什么关系？

**答法：** Skill 是可复用的任务说明与资源包，可以包含 `SKILL.md`、规范、脚本、模板；Prompt 是当前交给模型的上下文与指令；Tool 是执行具体操作的接口；MCP 是一种连接工具和资源的协议。它们不是一组互斥选型。

项目中 Skill 提供业务工作流，脚本或工具查询提供执行能力，评估器验证结果。当前工具调用实际通过 CLI／子进程完成，没有实现 MCP Server，不能把工具别名写成 MCP 接入成果。

### Q2：你是怎样搭建 Skill 的？Skill 由哪些部分组成？

**答法：** 本项目评估已有业务 Skill，我负责部分需按真实职责说明，不能把原 Skill 的脚本和模板说成自己从零开发。以数据库 Skill 为例，`SKILL.md` 定义适用范围和五阶段工作流；六份 references 细化意图、接入、分析、模板、三格式和最小交付；scripts 实现处理与渲染，templates 提供四类报告模板。金融 Skill 则约束识别输入、拆意图、取证、校验口径和评分。

如果问我怎样设计新的 Skill，我会从任务入口和验收条件开始，再决定哪些步骤需要脚本、哪些知识进 reference、哪些行为需要工具，最后配正反例回归。**这一段是设计方案，不是声称当前项目新写了两套业务 Skill。**

### Q3：Description 怎么影响触发？你验证触发准确率了吗？

**答法：** Description 应说明何时用、处理什么输入、交付什么，并排除容易误用的邻近任务。当前数据库 description 包含本地输入、四类报告、三格式输出和触发词；金融包含财报、行情和事实核查等任务。

但当前 runner 明确要求读取 `skill/SKILL.md`，这是定向执行评估，**没有验证运行时自动选择 Skill 的召回率和误触发率**。如要验证，需另建正例、近似负例、多 Skill 冲突和中英文改写任务，记录是否触发正确 Skill、是否多余触发。

### Q4：Reference 是自动加载的吗？怎样控制上下文成本？

**答法：** 不能仅凭目录存在就认定自动加载，取决于运行时和模型实际读取行为。本项目要求先读 `SKILL.md`；数据库主文档再规定各阶段应读哪些 reference，是否执行需查事件轨迹。运行器没有实现通用的自动 reference 加载器。

当前数据库 Skill 还存在“完整遵守所有规范”的要求，不能把它包装成已验证的按需加载优化。后续可精简主入口、将长规范按阶段索引，比较加载 token、任务成功率和漏约束率；目前没有前后对照，不能声称节省了多少 token。

### Q5：Tools 是你怎么设计的？

**答法：** 新增 `tool.py` 是受控测试替身，通过工具名、命令和参数选择固定回执，记录实际参数、状态、时间、响应哈希到 `tools.jsonl`。Agent 必须真实执行命令获得证据；Judge 再检查实际回执及 `evidence_id`，不能只相信回答里说“已查询”。

当前替身只覆盖有限命令；search 不严格匹配查询语义，也没有实现真实 API 的分页、限流或复杂重试，因此适合验证受控行为，不能证明真实检索质量。

### Q6：工具失败后怎么处理？为什么不直接重试？

**答法：** 先区分失败类型：请求不完整应澄清，证据缺失应说明不足，密钥缺失应停止并引导配置；只有可恢复的瞬时故障才适合有限重试。没有证据时不能用模型记忆补出确定数字。

当前项目已用配对用例检查缺依赖和安全停止；没有实现生产级退避重试、熔断或幂等治理。测试中故意设置工具不可用，正确停止是 PASS；执行器本身因额度或超时无法完成，是 BLOCKED。

### Q7：Skill 到底提高了多少效率？

**答法：** 当前能证明流程被标准化、用例可复跑、证据可留存，不能给出效率提升百分比，因为没有同任务、同模型、同工具的有／无 Skill 对照。记录的耗时和 token 是成本观察，不等于效率增益。

后续预先固定任务与验收规则，对比无 Skill、仅入口说明、完整 Skill 三组，评估完成率、错误放行、工具次数、总耗时和 token。必须同时看质量，不能只看回答更快。

### Q8：接入了什么业务系统？MCP 的价值是什么？

**答法：** 当前是本地评估工程，被测业务为数据库报告和金融核查；受控 Agent 调用替身，`live.py` 另行调用真实 westock／资讯依赖。没有线上业务系统、真实金融 Agent 端到端或 MCP 接入的证据。

若未来通过 MCP 暴露工具，应设计清晰的输入输出 schema、错误语义、权限和日志，并保留固定快照用于回归。但 MCP 不会自动解决数据正确性或模型误用问题。

## 四、三个最值得讲深的案例

### 案例 A：报告三个格式一致，为什么仍然判失败？

**S｜背景：** 数据库 Skill 将日志加工成多种格式的报告，输出之间一致仍可能共同复制上游错误。

**T｜任务：** 验证报告保留真实数据库身份与时长，并能将错误定位到具体处理层。

**A｜行动：** 对照原始日志、组件实际值与源码，使用独立 oracle 锚定 `Duration:` 和 `DB:`，避免复用被测解析器；进一步检查 `log_parser.py` 的宽泛 `(time|时长|duration)` 匹配，以及适配器把测试工具 `engine` 当数据库产品的路径。

**R｜结果：** 确认 D01 将原始 300 秒输出为 2026 秒、将 TDSQL-B-v22.7.2 输出为 sysbench，并给出代码定位依据；独立检查将该用例判 FAIL，未因多格式存在或一致而放行。尚未完成业务修复后的验证。

**修复建议与验收：** 分离测试工具与数据库产品，锚定字段；回归正常日志、不同起始年份、不同字段顺序及缺字段情形，确认全部核心记录未变。本项目当前给出建议和失败证据，未完成业务修复闭环。

### 案例 B：为什么必须同时测 0 和 null？

**S｜背景：** 数据接入同时需要兼容多种输入形式，并对关键指标执行质量门控，错误补值或丢记录会污染后续分析。

**T｜任务：** 区分真实零值与字段缺失，验证关键指标为 null 时能正确停止，并检验标准粘贴对象入口。

**A｜行动：** 设计零值、数组空值、标准粘贴对象及对应有效输入，核对输出记录数量、身份和数值；追查 `adapter_local_rows` 中的 `or` 提取与 TPS／QPS 兜底，以及将 `{meta, records}` 整体包装成一行的入口处理。

**R｜结果：** D16 预期两条记录、实际仅保留一条；D17 的 null QPS 未按要求停止；D07／D08 暴露标准粘贴对象适配问题。代码定位说明 `or` 会混淆 0 和缺失，TPS 补 QPS 会掩盖缺失，为修复和回归提供了明确检查点。

**更深的点：** 数据质量门控必须在丢弃或补写之前保留原始信息，否则后面的质量检查可能再也看不到缺失。D07 的 Agent 能直接检查完整 records 并停止，不代表原入口适配器已修好。

**修复验收：** 覆盖字段不存在、null、0、正常值、非法字符串，并检查记录身份和数量；不允许无依据补值。当前只确认缺陷与建议，不声称修复生效。

### 案例 C：报告高分，为何仍然失败？

**S｜背景：** 专项报告可能生成了表格和总结，却采用了比用户要求更宽的分析范围，形式完整不代表任务完成。

**T｜任务：** 验证 D04 是否按 3 个产品 × 2 个写入场景 × 2 个并发档筛选 12 条目标记录，比较 QPS／P95／P99 并给出选择依据。

**A｜行动：** 将用户要求转成目标记录集合与 mandatory 检查，独立筛选预期记录，核对分析范围、P99 和选型依据；将质量分数与任务通过状态分别记录。

**R｜结果：** 识别原分析按更宽范围分桶、仅给平均 QPS／P95，缺目标 12 条记录、P99 和明确选型依据，将 D04 判 FAIL。其他流水线用例即使超过 90 分，仍因强制交付缺项保留失败，避免高分掩盖必需项遗漏。

**修复验收：** 分析前保存目标记录集合，以产品／场景／并发身份逐条核验；同一集合用于表、图和结论。禁止只在全文搜索到 P99 一词就算完成：当前部分语义检查较浅，需继续加强。

## 五、测试开发岗位常见追问

### 1. 44 条用例是怎么选出来的？为什么不是越多越好？

以需求和风险拆维度，再覆盖关键分支：正常、异常、边界、等价输入、逻辑组合、红线。先保证用例有可区分的预期结果，再考虑数量。当前 44 条仍不足以证明全面覆盖，应按线上风险继续补，而不是称为完整场景穷尽。

### 2. 怎样减少多变量混杂？

固定公司、日期、问题和证据，只切换待研究变量。F10／F11 请求相同，仅资讯依赖状态变化；F01／F12 仅结构化依赖状态变化。否则“缺公司又缺工具”的失败不能明确归因。

### 3. Oracle 和业务实现都写错怎么办？

独立实现降低共享错误，但不是绝对保证。需要原始数据可读、手工抽核、官方来源记录和正反例。当前官方财报字段是整理记录，未在本次求职整理中重新联网下载原报；来源版本与后续更正也需要管理。

### 4. 38 项校准算不算变异测试？

它是针对已知错误模式，故意破坏输出的校准测试，可称“变异校准”或“正反例测试”。没有使用通用变异工具生成程序变异体，也没有统计 mutation score，不能写成获得了变异覆盖率。

### 5. 为什么 11/20 通过，分数却是 63.45？

11/20 是用例通过比例 55%；63.45 是六维适用检查的加权得分，两者不同。维度内先计算适用检查通过比例，套件内再按适用用例求均值，最后按权重汇总。N/A 不进入分母，不能把分数当通过率。

### 6. 具体权重是什么，是否具有统计最优性？

R1 输入意图 15、R2 接入证据 20、R3 真值口径 20、R4 分析评分 20、R5 交付追溯 15、R6 停止安全 10。它是任务风险驱动的设计选择，没有数据证明“最优”。因此用 mandatory／fatal 保证关键要求不被加权平均冲淡。

### 7. N/A、BLOCKED、REVIEW 有什么区别？

N/A 是某检查维度不适用；BLOCKED 是执行前提或运行条件不足；REVIEW 是仍待语义复核。三者都不应伪装成业务成功。应同时展示计划数、实际执行范围、状态和适用项得分。

### 8. 6 次流水线失败，是否说明框架不好？

测试框架的目标是可信地发现问题。被测脚本退出成功并产生产物，但缺强制交付、错误数据或遗漏范围，判 FAIL 正是预期功能。仍需用裁判正反例证明不是误杀，并保留实际证据。

### 9. 为什么不全部上 Agent 端到端？

端到端成本较高且定位困难。组件层快速检验解析和数据规则；流水线检查完整产物；Agent 层检验读取规范、工具选择、异常解释和交付。当前不是所有业务分支都完成端到端，D01 完整交付曾 360 秒超时，应保留为覆盖缺口。

### 10. 这算性能测试吗？

项目评估“数据库性能测试报告”的正确性，并记录 Agent 耗时和 token。没有并发压测、负载模型、吞吐曲线或 JMeter／Locust 实测，不宜写成性能测试平台。现有数据可支撑成本和耗时观察，但尚未建立业务 SLA。

### 11. 如何回归、如何进 CI？

当前可通过 `check`、`calibrate`、`component`、`pipeline`、`agent` 复跑，产物目录禁止覆盖；CI 集成尚未完成。尤其 `run.py` 将被测任务失败视为一次正常评估完成，进程可能退出 0；CI 应解析汇总 `decision`、失败及阻塞状态，不能只看退出码。长跑前还应补进程树清理。

### 12. 数据库、Redis、MQ、Kafka 你用过吗？

这个项目处理离线性能数据，没有实际连接 MySQL／Hive 或使用 Redis／MQ／Kafka 的证据。若有其他课程或项目经历可补；不能因为输入来自数据库测试，就声称自己实现过数据库调优或中间件链路测试。

## 六、Agent 与 AI 平台岗位常见追问

### 1. 怎样证明工具真的被调用？

查 `events.jsonl` 中的实际执行，再查替身写入的 `tools.jsonl`：工具名、命令、参数、状态与 payload。Judge 校验回执属于提供的夹具，答案 facts 的 evidence_id 对应成功回执，再核对值是否忠于引用。仅在回答中写“根据工具查询”不算证据。

限制也要说明：替身轨迹和夹具位于 Agent 工作区，缺少强物理隔离，不能宣称抵御恶意 Agent 伪造的安全边界已经完备。

### 2. Tool Calling 与 Function Calling 你实现的是哪一层？

当前通过 Codex CLI 的执行能力调用 Python 工具替身，使用 JSON Schema 约束最终输出；没有直接开发 OpenAI／Anthropic／Gemini 的原生 Function Calling 适配。结构化最终答案和模型发出的工具调用请求是两个不同环节，不能混为一谈。

如果后续接多厂商，可设计最小适配层，统一调用标识、工具名、参数、工具结果和错误，再处理各厂商消息结构及流式参数差异。这是后续设计，不是当前成果。

### 3. JSON Schema 能保证正确吗？

只能约束形状、类型和枚举，不能证明数值、来源或推理正确。当前 facts 还需独立真值和引用检查，answer 自由文本再单独复核；因此没有把“合法 JSON”当成业务成功。

### 4. 数据可信度为什么不能只按工具优先级？

工具优先级决定取证顺序，不代表数据天然真实。必须检查对象、日期、单位、币种、报告期和官方来源。当前真实依赖回执存在与官方财报口径不一致的数据；需要核对字段和换算，不能仅因接口退出 0 就认定真值成立。

### 5. 未知为什么不打 0 分？

0 表示有效证据否定核心断言，null 表示主需无法确认或没有候选答案可评分。把未知写成错误会误导用户，也会污染评估。主需与次需分开后，主需正确但额外归因无依据，可以是 1 分。

### 6. 多来源冲突如何处理？

先对齐口径，再定位冲突来源；有官方披露时核查权威记录，不能简单投票。若仍无法解决，就保留冲突和证据不足。当前 `conflict` 字段的公开语义还有歧义，后续应明确是“来源互相冲突”还是“候选回答与证据冲突”，再作严格断言。

### 7. 如何避免 Agent 看到标准答案？

`public_prompt` 从 input 白名单构造请求，只复制业务 Skill、附件和工具快照，gold 由父进程裁判持有。还通过校准测试检查请求不含标准答案。

但新会话和指令边界不等于强沙箱隔离。当前没有完成严格双盲或抵御恶意跨目录读取的验证，因此只能说明减少直接答案注入，不能声称绝无泄漏可能。

### 8. LLM 复核是不是自己给自己打分？

当前明确记录为 LLM 方法，不包装成独立人评。确定性检查先完成，复核记录含 reviewer、method、notes 和 response_sha256；自动 mandatory 失败不能被复核静默改成通过。若要更高置信度，应引入独立专家或盲评及一致性分析。

### 9. 哈希解决了什么，没解决什么？

解决版本和结果绑定：Skill／夹具／协议发生字节变化会被发现，复核记录不能应用到另一份答复。它不证明来源可信、结论正确，也不提供访问权限或不可伪造签名。

### 10. 为什么是金融 22/22，而不是全部运行都成功？

当前正式基线采用明确来源顺序中的首个兼容且已完成观察，额外兼容样本保留为重复；23 条不兼容或未完成记录有排除原因。这不是所有启动尝试的成功率，也不是 best-of-N 取最好分。评估应公开这个选择口径。

`collect.py` 当前检查请求尾部、固定时钟、工具夹具与 Skill 字节，并限制同模型；它没有对整个公开 prompt 做严格字节一致性校验。后续可保存规范化请求哈希和全配置签名，使兼容性更严谨。

### 11. 两组 3/3、第二模型 3/3 能证明稳定吗？

只能证明这些样本的观察结果。重复覆盖 F06、F08；跨模型覆盖 F01、F06、F08，占金融库 3/22。不能据此给出总体成功概率、生产可靠性或模型优劣排名，下一步应预先选择关键场景并扩大采样。

### 12. 你怎样看成本与延迟？

当前金融基线 22 条逐例耗时合计约 1131.686 秒，中位约 49.710 秒，CLI 回报 input 1,402,994、其中 cached 979,456，output 13,979。它们来自保存运行，不是本次整理的新模型调用，也不包括所有探索和超时。cached 是 input 子集，不能再相加；货币费用未知，不写成 0 元。

这些是整轮 Agent 数据，不是用户最终一句话的 token，也不能用长度不同的小样本直接比较模型性价比。

### 13. 为什么用标准库和 CLI，而不用 LangChain？

当前问题主要是用例执行、固定输入、日志收集和独立判定，标准库与已有 CLI 已能完成。引入框架需要有明确收益，不能只为堆技术栈。与此同时，这个选择不代表有 LangChain 使用实践；若岗位要求，需另补真实项目。

### 14. RAG、记忆和向量数据库在这里怎么体现？

当前没有这些模块。读取 Skill 文档或提供工具快照，不等同于构建 RAG。可以说明理解这些能力在复杂 Agent 中的用途，但不能说本项目已有检索索引、召回评估、会话记忆或向量库工程实现。

### 15. 如何说明 AI 工具参与和个人贡献？

如实区分：哪些需求、测试设计、实现、验证由自己完成，哪些借助 AI 生成。更有说服力的证据是能解释关键接口，现场修改一条校准反例，并判断为什么当前输出该通过或失败。不要把“我让 AI 做过”自动等同于已掌握所有工程细节。

```powershell
python -B -m unittest -v test_judge
python -B run.py check
```

第二条会新建一份自检目录，不覆盖原结果。还可以打开以下三组证据讲解：

2. `out/fin_review/F06-1/work/tools.jsonl` → `response.txt` → `result.json`：实际回执、3% 等号判断、通过依据。
