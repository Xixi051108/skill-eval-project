# Skill 评估答卷复盘

本次复盘核对了最终提交压缩包、两套评估材料、现存数据库执行产物及金融报告中的回答，并用腾讯官方公告核验了金融报告中的关键财报事实。提交压缩包内 16 个文件均与 `3 庄锐敏/` 下对应文件内容一致，因此以下判断针对实际提交版本。

没有评委反馈、正式评分和竞争者材料，无法确认真实淘汰原因。以下给出的是材料中可以证明的缺陷，以及这些缺陷为什么可能影响选拔。此次没有重新运行被测 Agent 或金融工具，所有运行观察均来自已有记录。

主要结论：答卷具备完整文档结构，也发现了一些有价值的缺陷，但没有充分建立从独立真值、真实执行、逐项判定到可靠结论的闭环。最严重的问题是错误财报被当成证据、明确错误的数据库产物仍被判通过，以及部分用户明确要求被降为增强项。

## 一 意图推理和理想态

### 已做对的部分

两套材料正确识别了本地数据边界、金融数据工具分工、四类报告、主要异常路径以及 0/1/2 真实性评分。这些说明已理解任务的大体范围。

### 主要缺陷

**1. 用户明确要求与实现完善度没有守住边界。**

DB-04 用户明确要求比较三个产品在两个写入场景、512 和 1000 并发下的 QPS、P95、P99，并给出产品选择建议。对应分析范围应为 3 × 2 × 2 = 12 条记录。这是任务本身的验收条件。

但 testcase 第 983 行将精确收敛到这 12 条记录称为“高标准的 custom 聚焦能力”。现存报告实际把五个场景、多个并发档混在一起分桶，只展示平均 QPS 和 P95，未完成要求的 P99 比较和产品选择，最终仍被描述为“部分通过但专项聚焦仍需完善”。

问题不在于允许部分得分，而在于没有清楚承认：本次用户任务的核心验收已经失败。可以记录路由、文件生成等子项得分，不能用它们替代任务完成度。

**2. 没有把未知与错误在评分上严格分开。**

金融报告 TF-06 在没有公司名称和报告期的情况下给出“真实性评分：0”，正文又表示无法判断对错。ideal_state 第 80 行允许证据不足时给受限分数，这让未知可以落入原本表示核心事实错误的 0 分。

这不是单条回答措辞问题，而是评测规范本身留下了混淆空间。应分别保存断言状态 `supported / contradicted / insufficient_evidence`、运行状态，以及有充分依据时才给出的 0/1/2 分。无法确定时分数可以为空，说明原因。

### 修正方法

每项要求标出来源和层级：用户明确要求、Skill 明确约束、评测建议增强。按来源冻结验收规则；如需修改规则，保留版本、理由，并对同一批输出统一重新判定。

## 二 测试场景

### 主要缺陷

**1. 覆盖到了维度名称，没有充分覆盖维度内部的关键分支。**

数据库用例有 log、JSON，但没有实际 CSV、XLSX 输入案例；没有充分检验对比条件不一致、迭代点数不足等前提。金融用例有 0 分和 1 分评分案例，却没有一个独立、确定应为 2 分的正例；“只给金融问题、不提供候选回答”的入口也缺少专门用例。

因此 R1 到 R6 均有映射，只能证明维度被引用，不能证明该维度的主要能力均被测试。

**2. 环境失败场景有多个变量同时变化，无法可靠归因。**

TF-07 和 TF-12 都使用“某公司”，既缺核查对象，又设置工具依赖失败。Agent 即使没有检查依赖，仅因为不知道公司名称而停止，也可能表现得像通过。

TF-12 原始回答确实同时提到缺公司和无法调用结构化数据，但现有证据仍不足以独立证明依赖探测正确。

**3. 一部分场景过宽，诊断价值不够。**

TF-03 的“某研报”“相关龙头”“最近”均缺明确对象或时间。输出可以合理地自选公司和窗口，却无法稳定对照同一份真值。DB-01 与 DB-11、DB-03 与 DB-12 重用产物本身合理，但报告应区分独立运行次数和审计检查数。

### 修正方法

保留少量端到端场景，同时增加独立的边界案例。完整公司与日期不变，只切换工具是否可用；相同证据不变，只修改候选回答的核心数字、次要解释；行情固定时钟和交易日，覆盖 2.99%、3.00%、3.01% 等阈值。

“少用例、多覆盖”只能用于控制端到端成本，不能替代关键分支和故障隔离。此前笔记中 GPT 给出的少用例建议缺少这一限制。

## 三 测试样例库与真值

### 最严重的问题是缺少独立真值核验

金融报告 TF-01 把腾讯 2024 年营收写为 7129.90 亿港元、同比 16.74%，并把候选回答中的约 6600 亿元人民币、同比 8% 判成核心错误。TF-05 又复用了同样的财报值。

腾讯官方 2024 年业绩公告给出的营收是人民币 660.3 billion，即约 6603 亿元，同比增长 8%；年度报告精确列示为人民币 660,257 million，即 6602.57 亿元。

来源：

- [腾讯官方业绩公告](https://static.www.tencent.com/uploads/2025/03/19/81cb1f36bec218d27d6e0b24eec012b6.pdf)
- [港交所披露的腾讯 2024 年报](https://www.hkexnews.hk/listedco/listconews/sehk/2025/0408/2025040800667.pdf)

“约 6600 亿元”与精确数的差异需要预先规定精度和容差；增长归因也应单独核查。无论最终对整段回答给几分，都不能据错误的币种与财报数字认定其核心错误。港股上市不等于公司财报必然以港元列报。

现有报告没有附对应原始工具响应，因此无法进一步确定错误产生于工具、字段解释还是回答生成。这一归因应保留，不能直接断言由某一层编造。但评测侧没有发现并拦截这组错误，是可以确认的问题。

### 样例库的其他问题

- TF-08、TF-10 的夹具直接用自然语言告诉 Agent 哪个断言被支持、哪个没有证据。它们可以作为评分单元测试，但不足以证明能读原始财报、正确路由和独立取证。
- TF-02 使用“今天”，报告标注测试日期 2026-06-19，回答却称当前日期为 2026-06-20。没有逐次运行时间和固定时钟，无法复现相同条件。也不能单凭较早交易日的下跌数据否定另一个日期的涨幅断言。
- 输入对象内部包含 `expected_*`，但没有可复用 runner 明确说明哪些字段发送给 Agent、哪些仅供裁判。不能据此认定发生答案泄露，但边界应落实为代码和保存的实际请求。

### 修正方法

测试库分别保存用户请求、文件与工具响应夹具、裁判私有真值、允许误差、证据出处和版本。Agent 看到原始证据；裁判保存预期标签与分数。真实联网案例保存响应快照，固定夹具案例用于稳定回归，两者分开报告。

## 四 输入 Agent 执行

### 数据库部分的测试层级不充分

数据库 HTML 报告明确写明 DB-01 至 DB-04 直接调用 `scripts/run_pipeline.py`，DB-07 通过 `--intent` 输入。Codex 执行了这些测试，并不等于已验证 Agent 加载 Skill 后的完整行为。

这种测试能发现脚本缺陷，但没有完整验证 Agent 是否识别触发条件、读取相应 references、调用正确工具、面对缺数据时澄清、发现产物问题后修复，以及最终向用户准确交付。

DB-07 为定位空值门控，把 `{meta, records}` 转成实现能接受的 records 数组，并用预制 intent 执行。这个诊断有价值，但应记录为派生的组件测试。原始自然语言和标准粘贴数据入口的兼容性仍是另一个独立结论。

### 金融部分的执行证据不够完整

HTML 收录了声明为实际运行的最终回答，但提交包没有逐次工具调用轨迹、原始返回、模型精确标识、运行配置和完整失败记录。不能因此认定没有实际运行；问题在于评审无法独立复核。

结论多次使用“稳定”，但材料没有给出重复次数、不同运行的结果分布或跨模型比较。一次运行只能证明该次观察。

### 修正方法

分别记录脚本组件测试与 Agent 端到端测试。端到端测试从干净会话开始，只注入真实用户输入和允许的附件，挂载固定版本 Skill，保存调用轨迹、原始输出和产物。记录 case_id、run_id、模型标识、配置、时间和环境状态。对关键案例做多次重复，必要时比较另一基座。

## 五 Judge 与元测试

### 1. 评分条件没有形成一致的执行规则

金融 TF-03 的 required_actions 要求使用资讯工具，judge 却允许“协同思路或等价证据层”。这可能让只提到工具、没有取得对应证据的回答通过。实际回答承认资讯依赖未就绪，却仍被总览记为完成。

100 分 Rubrics 给了维度和扣分点，但没有完整交代不同用例的适用维度、N/A 如何处理、重复错误如何聚合、fatal error 是否否决整套结果，以及部分通过如何进入总体分数。报告也未给出逐维度实得分和扣分证据。

### 2. 明确错误的数据库输出被漏检

现存原始日志第 6 行为 `Duration: 300s`，DB-01 的 extracted_data 与最终报告却记为 2026 秒。报告还把数据库产品写为 sysbench。提交报告对 DB-01 给出的评价仍为基线通过、核心指标可追溯。

这证明“输出和中间文件一致”不是充分条件：如果中间文件已经解析错误，后续三个格式一致地复制错误仍应失败。必须增加原始输入到中间结果的独立核验。

DB-04 的现存报告没有完成 testcase 中“同时比较 QPS、P95、P99”和“给出产品选择建议”等基线条件，却仍按较温和的完善度问题描述。允许部分得分的前提是逐项列出未通过项，整体任务仍须失败。

### 3. 元测试主要检查形式，未证明裁判有区分度

db_report 元测试文档第 421 行明确说明没有给最终执行结果打分。两套元测试主要检查字段、映射和覆盖声明，没有展示裁判是否能拒绝一份格式齐全但数字错误的回答。

另有一个具体维护问题：DB-12 的 `advanced_checks` 下混入 `untraceable_l2_insight`、`fabricated_performance_metrics`、`internal_data_access` 等错误标识。它们看起来属于 fatal_errors 的一部分；若下游只读取 fatal_errors，会漏掉这些错误。

### 修正方法

确定性部分用程序检查：指标值、筛选集合、文件存在、单位、日期和计算结果。解释性部分可以用带锚点的人工或模型 judge，但应要求指出证据位置。

用一份正确输出和多份故意破坏的输出校准裁判：更改 QPS、把 300 秒换为 2026 秒、删除 DOCX、错换币种、把证据不足改为确定错误。验证裁判既能拒绝错误，也不会误杀正确答案。

## 六 结果和下一步建议

### 结果表达的问题

数据库报告已有真实缺陷观察，尤其 DB-07 发现 qps 为空时被默默补写，是有价值的测试贡献。被测 Skill 失败多，并不意味着评估答卷差；发现真实且可复现的失败恰恰体现评估能力。

材料的主要问题是误放行、错误事实未被识别、结论无法充分复核。金融报告把“已运行”“已完成”用于不同性质的案例，没有形成明确的 PASS、FAIL、BLOCKED 判定及逐项证据；数据库报告则混合了独立运行与重用产物审计。

### 建议按以下顺序修正

1. **先修评测真值和判定。** 纠正 TF-01、TF-05；为 TF-06 处理未知与错误的区别；重新审核 DB-01、DB-04；固定 TF-02 的时间口径。暂时撤回受影响的通过结论。
2. **再整理可复用样例。** 将原始夹具与私有 gold 分离，补足 2 分正例、输入格式、对比前提、迭代点数和单一故障案例。不要先扩写更多说明文档。
3. **校准裁判。** 把现有漏检本身做成元测试反例，确保错误输出确实不能通过。明确各维度适用范围、聚合与 fatal 策略。
4. **补 Agent 端到端证据。** 保留脚本测试，但不再将它替代 Skill 的完整行为测试。保存原始轨迹和每次运行配置。
5. **重做结果页。** 每个结论至少列出 case/run、适用条件、预期、实际、证据、逐项分数、最终状态和归因。被依赖阻塞的正常场景记 BLOCKED；故意注入依赖失败的案例，按预期安全行为判 PASS 或 FAIL。
6. **用回归证明建议有效。** 为每个优先修复项指定失败案例和复测条件；同一套冻结输入与裁判比较修复前后结果，报告任务完成率、错误放行情况、重复运行一致性及必要的成本数据。

如果以评审视角概括：这份提交证明了能整理评估规范、设计一些正常与异常案例，也能发现部分脚本缺陷；但尚不足以证明能建立一套可信、可复跑、能准确拦截错误的 Skill 评估体系。这是从材料本身最能支持的落选风险判断，不能替代评委的真实反馈。
