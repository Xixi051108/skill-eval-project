# Agent 补测结果

日期：2026-10-27。新增实现与观察单独存放在 `补测/`；原 `答卷` 2.4 的业务 Skill、用例、裁判及历史结果保持冻结。

## 1. 本次补的是什么

金融补测让 Agent 实际读取 Skill、调用原始金融工具、检查来源与币种、输出核查答案，再接受独立判定。此前的 `live.py` 只证明原工具能够调用，不能代替这条 Agent 链路。

数据库补测让 Agent 接收公开任务和附件，尝试交付 single、comparison、iteration、custom 四类报告，同时保留工具轨迹和产物。这里使用题目提供的性能数据生成报告，**没有重新对数据库发起压测**。

本轮在同一个 Codex CLI 运行器下使用 gpt-6.1-sol 和 gpt-6-luna，属于固定运行器下的跨模型观察。没有新增多厂商原生 Function Calling、RAG 或记忆系统。

## 2. 执行合同与批次

- 协议 `supplement-1`，推理档位 medium；与历史 high 档位分批报告。
- 金融选择 F01/F02/F15：正确候选核查、错误候选核查、只求真实答案。都是腾讯同一年度财报附近的问题，不能代表三个独立行业或全金融覆盖。
- 金融每任务最多 8 次工具调用、每次最多 50 秒，Agent 最多 240 秒。数据库每任务最多 420 秒；这是实验预算上限，不是业务 SLA。
- 原用例、固定日期锚点和允许附件不变。金融不加载旧工具夹具或私有 gold；独立官方字段留在裁判端，Agent 仅读取依赖文档并通过网关调用原工具。
- 金融判定使用营收 3 亿元、同比 0.5 个百分点的绝对容差，并检查事实名称唯一、本次成功 LIVE 引用。公开 prompt 规定了主事实名称，但没有显式解释跨币种事实的唯一命名方式，属于协议澄清不足；不能把本批当作历史 2.4 完全同条件重跑。
- 自动检查通过先记 REVIEW；来源支持与解释再作响应 SHA-256 绑定的 LLM 复核。LLM 复核不是独立人工评审，不能覆盖原自动 FAIL。
- `protocol.json` 在执行前记录配置和代码哈希，`out/code/` 保留实际运行的四份源文件。之后的离线审计另有代码哈希，不冒充协议原有检查。

首次金融 F02 和数据库 D01 因账户使用额度触顶而 BLOCKED，后续任务按计划标记 NOT_RUN。额度恢复后新建批次继续，未覆盖首次记录、未购买额度、未使用重置券。

## 3. 真实金融结果

| 用例 | gpt-6.1-sol | 秒 | gpt-6-luna | 秒 |
| --- | --- | ---: | --- | ---: |
| F01 正确候选核查 | PASS | 131.016 | PASS | 103.641 |
| F02 错误候选核查 | PASS | 110.235 | FAIL | 67.688 |
| F15 只求真实答案 | PASS | 154.907 | FAIL | 88.672 |

以上六个任务均完成 Agent 回合，合计 **23 次真实工具调用，23 份成功回执**，并完成六份明确标注方法的 LLM 复核。原自动结果在各任务 `automatic.json` 中，最终结果在 `result.json` 中。首次额度阻塞不混入这六个已完成回合的分母，也不删除。

按本补测合同，主模型 3/3 通过，第二模型 1/3 通过；已完成回合耗时中位数分别为 131.016 秒、88.672 秒。每模型每场景仅一次，执行时间和检索返回会变化，不能据此认定总体优劣、显著性能差异或最高性价比。货币费用未返回，保持未知。

### 3.1 一条成功链路的具体例子

F01 要核查“腾讯 2024 全年营收约人民币 6600 亿元、同比约 8%”。主模型先查询结构化财报，发现 2024 年度行以港元列示，约 7129.90 亿港元；不能直接拿它否定人民币断言。随后两次资讯检索，在第三份回执中取得第一财经、证券时报网及腾讯网刊载摘要，支持人民币 6602.57 亿元和约 8% 的口径。回答给候选真实性 2 分，并明确未取得港交所公告全文。

这里的“评分 2”评价用户给的候选回答；测试 PASS 评价 Agent 有没有正确完成核查。这是两种不同评价。

各报道相互一致不证明它们的信息来源独立。本次未让 Agent 直接下载官方公告全文；独立官方字段来自冻结的 `答卷/sources.json`，不能误述为本轮新增官方原文联网验证。

### 3.2 两条失败的根因

第二模型的 F02/F15 正文均给出正确人民币答案，也披露港元口径差异；但是 facts 中用同一个 `revenue_yi`、`currency` 等名称重复记录两个币种。

```json
[
  {"name": "revenue_yi", "value": 6602.57},
  {"name": "currency", "value": "CNY"},
  {"name": "revenue_yi", "value": 7129.90},
  {"name": "currency", "value": "HKD"}
]
```

补测裁判要求唯一事实名。检测到重复后，按名字索引时后值又覆盖前值，触发人民币真值不匹配。因此保留当前规则下的 FAIL，也不能把所有失败断言算作独立金融推理错误。**本批公开 prompt 没有明确告知事实名称唯一或多币种该如何表示，规则与公开接口说明不充分，不能把这两条结果直接解释成模型金融能力差。** 更好的表达可使用 `finance_currency_type` 等不同名称；若改成复合业务键，应先澄清公开合同并校准，在新协议下执行，不事后放宽当前批次。

JSON Schema 只能证明字段类型满足结构，无法自动保证“列表中 name 属性唯一”。这类约束需要额外断言。

### 4.1 已确认的裁判格式局限

主模型 D01 自动为 FAIL／89.74，三条失败检查均为“正式报告逐行符合原始数据”。报告表格增加了“记录时间”列，而冻结 Judge 的 `normalized_table_rows` 只接受六列，实际没有读到七列表格。

新增离线 `audit.py` 按明确表头定位场景、并发、TPS、QPS、P95、P99，不依赖固定列位置，并对 MD/HTML/DOCX 各 30 行、各 120 个性能数值独立核对，均匹配。保留原 FAIL，另存 `table_review.json`；不能把已确认的格式漏读算作业务数值错误，也不能用局部审计直接宣称整个报告完全合规。

该 Agent 在自己的生成脚本中，从原始 DB/Duration 字段补偿了内置解析器的元数据错误，没有修改冻结 Skill。由此得到的是 Agent＋Skill 组合的任务结果，**不证明原业务解析器已经修复**。

### 4.2 过程证据怎样看

| 问题 | 观察证据 | 不能据此推断 |
| --- | --- | --- |
| 是否读规范 | events 中实际读取 Skill/reference 的命令和输出 | 模型已经理解并执行全部规范 |
| 是否实际执行 | 运行生成脚本的命令、退出码与产物 | 只读过 run_pipeline.py 就执行了流水线 |
| 是否忠实用数据 | 原附件、提取 records、独立数值对照 | Agent 自检说 PASS 就无数据错误 |
| 是否做对分析 | 版本顺序、独立回退集合、专项业务键集合 | 输出数量正确就范围正确 |
| 是否完成交付 | 三格式、图表、相对路径、中间文件和最终答复 | 文件存在就排版与内容全部正确 |
| 是否保持被测对象 | 原 Skill/输入的字节检查 | 环境具备抵抗恶意进程的强物理隔离 |

`process.json` 的字符串匹配是线索，可能把读取脚本记成 pipeline_request；本结论需要结合实际命令和产物复核。分析方案文件存在，也不能反推执行前已经独立审议过方案。

### 4.3 另外两种裁判适配局限

两个模型的 D04 均实际给出了 12 条正确子集和逐场景选型建议，主模型中间 JSON 使用 `custom.buckets`，第二模型把子集放在 extracted.records，建议均写在正式报告中。原 Judge 仅读取 `selected_records/focused_records` 与 `recommendation/selection`，未识别这些等价产物；公开任务和 Skill 没有强制这几个内部键。独立子集审计确认两个模型的目标记录均正确，原自动 FAIL 保留，不能说成业务遗漏 12 条记录。第二模型另有重复第3章标题及约11.0%相对增幅与原数据约11.17%不一致的问题，故不能把局部正确扩展为整个报告合规。

第二模型 D01 将全部报告写到 `artifacts/single/`，裁判固定找 `artifacts/data/`，因路径未匹配而提前失败。原公开 prompt 仅要求报告写入 `artifacts/`，没有明确排除子目录。实际子目录中的提取数据及三格式各 30 行均通过离线核对。这暴露产物发现与公开目录说明的缺口，不是“完全没有报告”。

### 4.4 自动高分仍可能漏掉交付问题

第二模型 D02 自动 REVIEW／100，数值与文件检查通过，但最终答复承认新增图表存在中文字体问题。独立抽看 32 张图中的 3 张：两张内置 comparison 图中文正常，一张 `product_1_oltp_point_select.png` 的标题和坐标轴确实出现缺字方框，故语义复核 FAIL。原自动结果保留，`visual_review.json` 记录抽查范围与图像哈希。

不能把抽查发现扩大成“32 图全部乱码”；也不能因正文、数值与文件存在就忽略已经证实的图表可读性问题。

## 5. 实现与验证边界

宿主网关调用课程原 Node/资讯 Python 脚本；真实密钥不注入 Agent 子进程。Agent 通过 localhost 的会话能力调用允许的只读工具。回执保存命令参数、退出码、耗时、源码与脱敏输出哈希。超时终止所属进程树，额度失败明确记录并停止后续任务。

`tools/` 保留实际运行的原工具字节快照。仓库原有 westock 脚本与该快照规范化换行后相同，但原字节哈希不同；原目录未覆盖。复跑需匹配回执脚本哈希时使用 `--tools-root 补测/tools`，密钥仍从本地环境提供，快照不含凭据。

这不是新造了一套金融数据库，也不是多厂商协议层；环境变量清理与日志脱敏也不等同完整安全审计。实际模型运行需要已有账户权限；接入真实工具需要相应金融服务凭据。

离线审计覆盖提取记录与原始数据的身份及核心数值，并对 D01 三格式逐行检查。未进行 Word 人工分页、浏览器截图或全部图表的独立视觉验收；不得把 Agent 自述的检查数量当成独立测试数量。

验证结果：本轮补测工具 **12/12 本地测试通过**，原答卷冻结检查 **255/255 通过**；校准用的模拟密钥不是真实凭据。旧 38 项校准作为原 2.4 已有记录保留，不与本轮 12 项混称成 50 条业务测试。

收尾验证曾有两次整套测试在错误鉴权请求处遇到 Windows 10053 连接中止，单项重测通过。鉴权先于请求体解析，测试改用无正文的未授权请求后，整套 12 项通过；仍保留 `checks-first.txt`、`checks-second.txt`。这项鉴权测试修正仅调整无关请求体，不涉及运行时网关或金融客户端，也不声称已经完全定位 Windows 底层中止原因。

另外发现，运行时版本的网关先对脱敏文本算哈希，再按 Windows 默认规则写文件，导致落盘字节多一层换行转换。全部 23 份回执在逆转这一层写入转换后与原 stdout_sha256 匹配；`receipt_review.json` 另记实际文件字节哈希。原回执不覆盖。运行结束后将网关写入改为不转换换行，并在原测试中加入 CRLF/LF 混合文本的字节哈希断言；该修正只经过本地测试，没有重新运行金融 Agent，也没有改变本轮模型成绩。

## 6. 仍然缺什么

- 本轮只补代表场景，没有完成 44 条用例×两个模型的全量 Agent 执行，也没有重复稳定性实验。
- 金融围绕同一份历史财报，公开事实可能存在于模型先验中；带数字检索存在确认偏差风险。不能宣称未知事实泛化或排除记忆影响。
- 未完成官方公告全文的真实抓取与逐字段核对，媒体转载的来源独立性也未证明。
- 裁判存在格式适应与语义支持关系的局限；事后审计留证据，下次应在新协议下校准后重跑。
- 原业务 Skill 的缺陷未整体修复并回归；独立专家人评、生产运行、费用测量和多厂商原生协议适配尚无本项目完成证据。后者是岗位补强方向，不是导师答疑中的既定交付要求。
